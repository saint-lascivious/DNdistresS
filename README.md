## What Is It?

```text
DNdistresS is a controlled DNS workload generator.

It repeatedly queries domains with configurable rate, burst, concurrency
runtime, resolver target, query type, source lists, and caching behaviour.

It makes DNS traffic on purpose, in ways you can shape.

It can make a lot of it, a little bit of it, or a very specific amount of it.
```

## OK. Sure, I Guess. Why?

```text
DNdistresS exists to answer a question that no one asked:

"What if I wanted to poke and prod my DNS servers any which way I wanted, but
for some reason all I have is a POSIX shell, a handful of built-ins, and a few
common utilities?"

Use it for cache priming, baseline and stress comparison, change validation
reproducible resolver/network tests, interrogation, and automation whenever a
repeatable DNS workload is desired.

DNdistresS generates predictable domain name server pressure, helping to find
limitations before they find you, and to validate that changes have the
intended effect.
```

## examples

```text
Topic: examples

Quick start:

  # Download the raw script and make it executable.
  curl -fsSL 'https://raw.githubusercontent.com/saint-lascivious/DNdistresS/master/DNdistresS' -o DNdistresS && chmod +x DNdistresS

  # Same same, but wget flavoured.
  wget -qO DNdistresS 'https://raw.githubusercontent.com/saint-lascivious/DNdistresS/master/DNdistresS' && chmod +x DNdistresS

  # Local resolver, fixed RR type, quiet output.
  DNdistresS \
    --location local \
    --local 127.0.0.1 \
    --type A \
    --qps 32 \
    --burst 8 \
    --maximum 4 \
    --duration 60 \
    --output quiet

  # Remote resolver with an explicit port and a modest runtime.
  DNdistresS \
    --location remote \
    --remote 1.1.1.1#53 \
    --type AAAA \
    --qps 64 \
    --burst 16 \
    --duration 5m

  # Multiple local resolvers, round-robin strategy (default).
  DNdistresS \
    --location local \
    --local 127.0.0.1,127.0.0.2 \
    --resolver-strategy rr \
    --qps 64 \
    --burst 16 \
    --duration 3m

  # Multiple remote resolvers, random strategy.
  DNdistresS \
    --location remote \
    --remote 1.1.1.1#53,8.8.8.8#53,9.9.9.9#53 \
    --resolver-strategy random \
    --qps 96 \
    --burst 24 \
    --duration 5m

  # Mixed repeated --remote flags with IPv6 and explicit ports.
  DNdistresS \
    --location remote \
    --remote 1.1.1.1#53 \
    --remote '[2606:4700:4700::1111]:53' \
    --remote '[2001:4860:4860::8888]:53' \
    --resolver-strategy rr \
    --type AAAA \
    --qps 64 \
    --duration 4m

  # Parallel fanout across all active remote resolvers (advanced).
  # Mirrors each logical query to every resolver while enforcing a global
  # backend QPS/burst/batch budget.
  DNdistresS \
    --location remote \
    --remote 1.1.1.1,8.8.8.8,9.9.9.9 \
    --resolver-strategy parallel \
    --qps 32 \
    --burst 8 \
    --maximum 8 \
    --duration 2m

  # Read from a local file instead of downloading a source.
  DNdistresS \
    --file ./domains.txt \
    --format plain \
    --top 1000 \
    --output answer

  # dig backend with custom dig options and batching.
  DNdistresS \
    --binary dig \
    --dig-options '+time=2 +tries=1 +retry=0 +notcp +ignore' \
    --dig-options-mode append \
    --batch 16 \
    --qps 128 \
    --burst 32

  # Random RR types with auto-tuning.
  DNdistresS \
    --random \
    --auto-tune \
    --allow-any \
    --location auto \
    --qps 128 \
    --duration 10m \
    --output answer

  # Install everything in one go.
  DNdistresS install /usr/local/bin --full

  # IPv6 resolver forms.
  DNdistresS --local ::1 --location local
  DNdistresS --remote '[2001:4860:4860::8888]:53' --location remote

  # Top filtering with multiple patterns.
  DNdistresS --top 5000 .com .net .org
  DNdistresS --top 1000 ||google.com
  DNdistresS --top 2000 ^cloud

Notes:
  - Use --help runtime for query pacing details.
  - Use --help dig-options for dig-specific flags.
  - Use --help auto-tune for warmup and estimation algorithm and behaviour.
  - Use --help top for filter syntax.
```

## description

```text
Topic: description

DNdistresS continuously (or time-bounded) sends DNS a configurable volume of 
queries of any type from a prepared domain top domains list and/or custom list,
using token-bucket scheduling and a worker pool.

Whether it's a trickle of queries or a flood, in bursts or at a constant rate,
on demand or as a periodic background task, with dig or nslookup, DNdistresS
is designed to generate controlled DNS traffic for cache priming, testing,
benchmarking, or otherwise simulating workloads against resolvers.

Key properties:
  - Deterministic rate shaping via qps + burst
  - Parallel execution via worker pool
  - Flexible domain source handling (download/cache/file/custom list)
  - Resolver targeting (local/remote, IPv4/IPv6, port)
  - Query tool selection (dig/nslookup) and RR type selection

DNdistresS is an impractically complex resolver workload tool for controlled DNS
traffic generation.

See also:
  --help what
  --help why
  --help info
  --help examples
```

## runtime

```text
Topic: runtime

Data path:
  Domain source(s) -> parser -> deduplication -> top-N -> dispatch -> workers.

Primary controls:
  -q/--qps          tokens per second
  -B/--burst        burst ceiling
  -m/--maximum      worker count
  --batch N         dig batching size (enables batching)
  -D/--duration     runtime seconds (0 = forever)
  -o/--output       quiet|answer
  _CLOCK_TICK_MS    scheduler tick cap in ms (env var)
  _DRAIN_TIMEOUT_MS max graceful drain wait after duration stop (env var)

Secondary controls:
  --force-maximum   override default max worker clamp (128)

Timer guard:
  When running under DNdistresS.service from DNdistresS.timer,
  _DURATION may be clamped to the detected timer period to prevent
  overlap/runaway execution.

  If timer period cannot be auto-detected, set _TIMER_PERIOD explicitly
  (duration syntax, e.g. 1h) to enforce the guard.

See also:
  --help qps
  --help burst
  --help maximum
  --help batch
  --help auto-tune
  --help clock-tick-ms
  --help drain-timeout-ms
```

## auto-tune

```text
Topic: auto-tune

Meaning:
  Auto-derive worker count (_MAXIMUM) and burst size (_BURST) before the main
  run.

Enable:
  --auto-tune

Defaults:
  _AUTO_TUNE_SAMPLES=10
  _AUTO_TUNE_BURST_WINDOW_MS=250
  _AUTO_TUNE_TRIM_PCT=10
  _AUTO_TUNE_PERCENTILE=95
  _AUTO_TUNE_PCTL_MAX_RATIO=4
  _AUTO_TUNE_MAX_GROWTH_FACTOR=5

Sample-count selection:
  - _AUTO_TUNE_SAMPLES is the base sample count.
  - If both _AUTO_TUNE_SAMPLES_MIN and _AUTO_TUNE_SAMPLES_MAX are set to valid
    positive integers and MAX >= MIN, sample count is randomised uniformly in
    [MIN, MAX].
  - If only one of MIN/MAX is set, range mode is ignored and
    _AUTO_TUNE_SAMPLES is used.
  - Sample count is clamped to available domain count when necessary.

Warmup domain selection:
  - Warmup domains are selected randomly (without replacement) from the active
    domain pool, not taken from the head of the list.
  - Active pool means domains after parsing/validation, deduplication, and
    active top/filter selection.

Mechanism:
  1) Warmup:
     Run a short synchronous probe over randomly selected sample domains.
  2) Estimate:
     - collect latency samples (ms)
       (per-query in non-batch mode, per-batch when dig batching is active)
     - trim low/high outliers by _AUTO_TUNE_TRIM_PCT
     - compute median (p50) and target percentile (_AUTO_TUNE_PERCENTILE)
     - cap percentile to: pctl_ms <= p50_ms * _AUTO_TUNE_PCTL_MAX_RATIO
  3) Derive:
     batch_effective = (_DIG_BATCH_SIZE_EFFECTIVE when dig batching is active, else 1)
     _MAXIMUM ~= ceil((_QPS / batch_effective) * (pctl_ms/1000) * 1.2)
     _BURST   ~= ceil(_QPS * (_AUTO_TUNE_BURST_WINDOW_MS/1000))
     if batch_effective > 1:
       - _BURST is raised to at least batch_effective
       - _BURST is rounded up to a multiple of batch_effective
  4) Guard:
     tuned workers per run are capped to:
       current _MAXIMUM * _AUTO_TUNE_MAX_GROWTH_FACTOR
     (unless --force-maximum / -m N! is set)

You want I should give 'em the clamps?
  - If -m N! or --force-maximum is set, auto-tune will not change _MAXIMUM.
  - If -B N! or --force-burst is set, auto-tune will not change _BURST.
  - Baseline floor: without force overrides, auto-tune will not reduce
    _MAXIMUM/_BURST below their current configured values; it only raises
    them.
  - Standard safety clamps are applied after auto-derived values.
  - Ooh, that's gotta clamp!

Notes:
  - Auto-tune is best-effort and depends on current resolver/network/host
    conditions and how much I suck at writing selection algorithms.
  - If conditions change after warmup, achieved QPS can differ from the
    target QPS.
  - QPS is a target, not a limit; the actual achieved QPS may be lower or
    higher depending on various factors including but not necessarily limited
    to network conditions, resolver performance, cosmic rays, how much saint
    sucks at writing progressive selection algorithms, the phase of the moon
    and the alignment of the planets; especially Pluto, which is a known jerk.
  - If you are reading this documentation, you're probably trying to do
    something clever and/or evil with DNdistresS. I don't know what it is.
    Actually, I have a pretty good idea, but I can tell you that if you are
    trying to do something clever and/or evil with DNdistresS, you are very
```

## resolver-strategy

```text
Topic: resolver-strategy

Meaning:
  Selects how resolver endpoints are chosen from the active resolver pool.

Flag:
  --resolver-strategy MODE
  --resolver-strategy=MODE

Values:
  rr        round-robin endpoint selection (default)
  random    random endpoint selection
  fastest   preflight benchmark, pick fastest endpoint, then pin to it
  parallel  mirrored fanout to all endpoints per logical dispatch

fastest details:
  - Probes one domain from the active domain set (default: random).
  - Sends N probes per endpoint (_FASTEST_PROBE_COUNT, default 5).
  - Uses trimmed mean latency (drops min/max when N>=3).
  - Lowest trimmed mean wins.

  - In parallel mode, each logical query is mirrored to each endpoint.
  - Global backend budgets are enforced by charging one token per endpoint
    per logical query.

      floor(_QPS / endpoint_count)
```
